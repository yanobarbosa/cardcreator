Estamos iniciando um novo projeto chamado **Card Forge**.

Quero que você implemente a **Fase 1 / versão 0.1**, que será a fundação arquitetural de um aplicativo de criação e gerenciamento de cartas para um TCG próprio.

Leia todos os requisitos abaixo antes de começar.

## CONTEXTO

O projeto utilizará inicialmente a estrutura de cartas de Flesh and Blood como primeiro ruleset, mas **o aplicativo não pode ser acoplado a Flesh and Blood**.

No futuro deverão existir:

* ruleset FAB;
* ruleset próprio;
* outros rulesets;
* Obsidian;
* PWA;
* biblioteca;
* templates personalizados;
* deck builder;
* playtest.

Portanto, esta fase deve priorizar arquitetura e extensibilidade.

---

```ts

  cardTypes: CardTypeDefinition[];
```

# VALIDATION

Implemente validação estrutural simples.

Por exemplo:

```text

Hero sem Intellect → warning

Attack Action sem Power → warning
```

Estrutura:

```ts
interface ValidationResult {
  severity: "info" | "warning" | "error";

  code: string;

  message: string;

  field?: string;
```

# Card Forge

## Especificação inicial — Arquitetura e versão 0.1

### 1. Visão do projeto

**Card Forge** será uma aplicação para criação, organização e posterior playtest de cartas de um TCG próprio.

A primeira implementação utilizará a estrutura de **Flesh and Blood** como ruleset de referência, porém o aplicativo não deve ser programado especificamente para um único jogo.

A arquitetura deve permitir que, futuramente, existam múltiplos rulesets:

* Flesh and Blood;
* Nosso TCG;
* Rulesets experimentais;
* Rulesets criados pelo usuário.

A aplicação deverá funcionar prioritariamente como:

* aplicação web responsiva;
* PWA instalável;
* desktop;
* dispositivos móveis.

A arquitetura também deve permitir integração futura com **Obsidian**, utilizando o mesmo núcleo de dados, renderer e componentes sempre que possível.

---

# 2. Princípios arquiteturais

O projeto deve seguir algumas regras fundamentais.

## 2.1 Dados da carta separados da aparência

Uma carta não deve armazenar coordenadas ou informações específicas de layout.

Exemplo de dados:

```ts
{
  name: "Arc Lightning",
  type: "attack-action",
  cost: 1,
  power: 5,
  defense: 3
}
```

O template é responsável por saber onde essas informações aparecem.

Fluxo:

```text
Card Data
    ↓
Template
    ↓
Renderer
    ↓
Preview / PNG / WebP / impressão
```

---

## 2.2 Ruleset separado do Core

O Core não deve saber o que é:

* Attack Action;
* Hero;
* Pitch;
* Intellect;
* Equipment;
* Lightning;
* Guardian;
* Warrior.

Esses conceitos pertencem a um ruleset.

Exemplo:

```text
Core
├── Cards
├── Templates
├── Renderer
├── Storage
├── Validation
└── Ruleset API

Rulesets
├── FAB
└── Custom
```

---

## 2.3 Armazenamento abstrato

Nenhum componente React deve acessar diretamente:

```text
localStorage
IndexedDB
filesystem
Obsidian Vault
```

Deve existir uma interface comum.

Exemplo:

```ts
interface StorageAdapter {
  saveCard(card: Card): Promise<void>;
  loadCard(id: string): Promise<Card | null>;
  deleteCard(id: string): Promise<void>;
  listCards(): Promise<Card[]>;
}
```

Implementações futuras:

```text
IndexedDBStorageAdapter
ObsidianVaultStorageAdapter
FileSystemStorageAdapter
```

Isso permitirá que o mesmo editor funcione no navegador e no Obsidian.

# 7. Renderer

O renderer não deve estar acoplado à tela do editor.

Recomendação inicial:

**SVG como superfície primária de renderização.**

Motivos:

* textos permanecem nítidos;
* escala sem perda;
* clipping da artwork;
* layers simples;
* posicionamento absoluto preciso;
* fácil renderização no navegador;
* possibilidade de converter posteriormente para PNG/WebP.

O renderer recebe:

```text
Card
+
Template
```

e produz:

```text
SVG / Preview
```

Posteriormente:

```text
PNG
WebP
PDF
```

# 20. Critérios de aceite da versão 0.1

A fase estará concluída quando:

1. O projeto iniciar com um único comando.

2. O usuário conseguir criar uma carta.

3. Alterar o tipo da carta modificar automaticamente os campos disponíveis.

4. Alterar um valor atualizar instantaneamente o preview.

5. O renderer usar dados + template, e não markup específico da carta.

6. Uma carta puder ser salva.

7. Fechar e abrir a aplicação não apagar as cartas salvas.

8. Uma carta salva puder ser aberta novamente.

9. A aplicação funcionar corretamente em viewport mobile.

10. O Core não depender de React.

11. O Core não depender de Obsidian.

12. O ruleset FAB não estiver misturado ao Core.

13. O renderer não estiver misturado ao formulário.

14. Nenhum componente acessar diretamente o mecanismo de persistência.

15. O código estiver preparado para receber posteriormente um segundo ruleset.
